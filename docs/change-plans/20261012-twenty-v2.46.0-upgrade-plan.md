## D. Work sequence and gates

### Stage 0 — Target acceptance and recovery contract (STOP before implementation if incomplete)
- Confirm `twenty/v2.46.0` and `sdk/v2.46.0` commit IDs, **published** release notes, official self-host Docker registry image/tag/digest/architecture, known defects, required upgrade commands and Node/DB/Redis/SDK compatibility. If 2.46 unpublished/unstable, prepare against tag only, no live launch; reconsider the latest verifiable *published* point release (currently 2.45.0).
- Check publisher of each changed dependency, its official support/security advisories, transitive graph/lockfile and affected runtime; make only risk-justified scoped upgrades with rollback. Node 24.16.0, Yarn 4.13.0, Nx 22.7.8 are currently unchanged between compared roots. Validate target Docker build independently.
- Verify the owner-provided full migration document set and snapshot JSON; fresh complete *database + local storage + configuration* backups and **restore rehearsal**. Preserve effective `ENCRYPTION_KEY` and `FALLBACK_ENCRYPTION_KEY`; never print secrets.
- Identify ERP/API, Python, SharePoint, Power Automate and Windows scheduled writers; plan isolation on Test and pause/restart on Live. Do not assume Twenty core deployment stops those writers.
- **Gate 0 outputs**: pinned target record, security/dependency assessment, recovery plan and approved scope. No production deployment approval implied.

### Stage 1 — Source baseline and new upstream branch
- Re-verify upstream/fork refs; capture `git log` and full `git diff --name-status` for accepted `main` vs `twenty/v2.35.2`. Record ownership per file/commit, upstream renames and replacements through 2.46.
- Fetch exact upstream tag into local Git. Create a **clean target base branch** from that tag; port changes into an **implementation branch**, keeping clean base untouched. The current `permavent/upgrade-v2.46.0-preparation` is a documentation/control branch currently rooted at old main; do not mistake it for 2.46 source.
- Use per-feature patches/cherry-picks with conflict review and explicit replacement decisions. Do not run old `prepare-permavent-upgrade.sh` all-layer script by changing version strings; its branch names are stale and it omits opening tab.
- **Gate 1**: full file-level port checklist with accepted/rewritten/dropped (with justification) for every custom commit and helper.

### Stage 2 — Core port / focused regressions
- Sequence: minimal email branding -> config/flag contracts -> auth/delegation/Sales Scope -> audit/weekly report -> interpreter/runner -> UI wide panel/overview -> opening-tab integration -> original release helpers.
- Prefer upstream APIs to replacing large modules; keep feature flags and Enterprise licence boundaries. Do not casually activate RLS.

### Stage 3 — Apps/runner/external integration preparation

- **Gate 3**: app plans clean, SDK verified, runner/external effects signed off.

### Stage 4 — Isolated Test rehearsal

- Confirm all C-table behaviours and five Apps, permissions, sample CRM operations, custom schema IDs and fields, metadata 33/717 drift analysis, 8/308 custom inventory, workflows and attachment retrieval. Compare Test snapshot to Live baseline allowing documented upstream schema additions/removals.
- **Gate 4**: Test technical + functional acceptance and documented recovery rehearsal. Fixes require new image and rerun.

### Stage 5 — Image release and Live decision (separate approval)
- Build from verified pinned port with private GHCR release tag, attest source SHA / OCI index + amd64 digest, verify build dependencies and scanner findings. Do not reuse current tag.
- Obtain explicit owner approval, fresh Live database/storage/config backups and recoverability checks; isolate external writers and confirm disk space (35 GiB free at earlier check is not proof for new images/backups).

Confirm encryption/config preserved, worker and cron separation, source identity, health, `upgrade:status`, schema, app functionality, integration resume and director/user sign-off. Plan downgrade as DB **restore + matching image + storage/config**, not image-only downgrade after migrations.
- **Gate 5**: logged deployment, independent owner acceptance, rollback artefacts and handover.
