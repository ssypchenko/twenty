## 3. Migration and recovery contract

Upstream [target-tag upgrade guide](https://github.com/twentyhq/twenty/blob/twenty/v2.46.0/packages/twenty-docs/developers/self-host/capabilities/upgrade-guide.mdx) documents cross-version upgrades from `1.23+`, automatic server-start migrations, `upgrade:status` and preserving `ENCRYPTION_KEY`, with `FALLBACK_ENCRYPTION_KEY` relevant to our current runtime. There is no published proof that **our** custom data, functions or permissions survive until rehearsed.

**Baseline from uploaded owner files dated 2026-10-12**, not new server checks:
- Live: `/opt/twenty`, Test: `/opt/twenty-test`, same accepted image `v2.35.2-permavent.4`, PostgreSQL 16, healthy at snapshot date; Test backup/refresh helpers separately documented.
- Current image source `69da6b1d8c33d15ce4d9a81da01f6c859933458b`; Live and Test have environment differences. `PERMAVENT_SECURITY_RLS_ENABLED=false` both; Live-only weekly report and internal interpreter; Test disabled cron registration and has no runner token.
- Encryption and fallback encryption keys were present; values were deliberately not collected.
- Live timer `twenty-backup-live.timer` disabled; old Live deployment backups exist but **are not fresh current recovery**. Independent restore rehearsal not done. Old host free disk circa 35 GiB; not verified today via live SSH.
- Custom workspace-local App `1.0.1` owns eight objects, 308 fields; complete Live metadata recorded as 33 active objects and 717 active fields plus four Custom-app logic functions. Preserve IDs, relations, fields, functions, layouts and files.

**Before Test refresh / deploy (requires explicit separate authorisation):**
1. Read all operational runbooks `02`, `05`, `06`, `07`, `10` and their current JSON evidence. Re-check server versions, Compose mounts/volumes, all actual disk sizes and writer states via read-only server access.
2. Create *fresh*, protected and checksummed database (roles/global objects included), full local storage and configuration/secret recovery artefacts; confirm consistent capture and restricted access. Never place dumps, tokens or key values in Git.
3. Verify that restore uses **matching PostgreSQL 16, matching key material, storage, configuration and compatible image**. Practise independent restoration onto an isolated environment; prove row/object/field metadata, attachment and Custom-app function recovery, and reject accidental outbound integrations.
4. Record pre-migration schema and app fingerprints; `upgrade:status`, app IDs, key presence (not values), expected job/worker layout, backup checksums, retention, restore timings, free space, and owner acknowledgment.
5. Once migrations have advanced, **rollback means database + storage + configuration restore with a matching older image**, NOT simply changing Docker TAG. `twenty-promote-test-to-live` replaces Live data: never use it as a normal version upgrade.
6. Run all target migrations only on isolated Test first, inspect `upgrade:status` and all custom metadata and functional behaviour. Owner approval required separately for destructive Test clone and for Live.

**Gate status:** recovery *plan specified*, fresh backup/restore rehearsal *not performed*, so **blocked**.
